# Codexスキル候補一覧 — cosmic_id で繰り返し発生する作業の分析

作成: 2026-07-16(Fable)。Phase 0〜3(Issue #1〜15、PR #17〜28)の実運用ログから抽出。
分析の5観点: ①毎回同じ手順 ②判断基準が暗黙的 ③引き継ぎで失敗しやすい ④自動化可能 ⑤テンプレート化可能。
各スキルの末尾タグ〔①〜⑤〕はどの観点から抽出されたかを示す。

## S1. issue-to-pr(Issue実装の1サイクル)〔①④⑤〕

- **スキル名**: issue-to-pr
- **発動条件**: GitHub Issue が1つ割り当てられ、受け入れ基準が本文に書かれているとき
- **入力**: Issue番号。文脈は Issue 本文・AGENTS.md・docs/ORG.md から取る(プロンプトで再説明しない)
- **手順**:
  1. `git fetch origin && git checkout -B issue/I-<番号>-<slug> origin/main`
  2. Issue の「最初に読む」を読む → 実装(一番シンプルに)
  3. 意味のある単位ごとに commit(途中死対策。ORG.md v2 R1)
  4. `npm test` 全pass確認 → push → `gh pr create`(本文は S10 のPRテンプレート)
- **判断基準**: 受け入れ基準を全て満たすか/計算変更に「○○流に従う」コメントがあるか/変更が Issue のスコープに閉じているか(はみ出したら別Issue化を提案し、混ぜない)
- **出力**: `Closes #N` 付きPR。本文に実行結果(テスト実出力)と未確認事項
- **失敗しやすい点**: 古いmainから分岐してコンフリクト(必ず fetch してから分岐)/コミットメッセージ末尾の Co-Authored-By 忘れ/テスト未実走で「passするはず」と書く

## S2. pr-quality-gate(PRレビュー品質ゲート)〔①②⑤〕

- **スキル名**: pr-quality-gate
- **発動条件**: PRが作成され、レビュー担当(作者≠レビュアー)が割り当てられたとき
- **入力**: PR番号
- **手順**:
  1. `gh pr diff <N> --name-only` でスコープ確認 → diff 全読
  2. 計算系PRのみ: PRブランチで `npm test` を独立実走+作者が使っていない抜き打ちケースをnodeで1件検証
  3. docs/CSS系PR: diff読取りのみ(再検証しない — コスト規律)
  4. 結果を `gh pr comment` でチェックリスト形式で記録(マージは人間)
- **判断基準**: テスト実出力が貼られ全pass/受け入れ基準との対応/AGENTS.md禁則(escapeHtml・プレミアムロック・関心の分離)/範囲外変更の混入なし。**2回差し戻しで担当を1段上のモデルへ**(Sonnet→Opus→Fable)
- **出力**: 「✅合格/差し戻し」のPRコメント(検証は何をレビュアー側で独立実走したか明記)
- **失敗しやすい点**: 作者の検証結果を鵜呑みにする(独立実走が原則)/同一アカウントPRはGitHub仕様でapprove不可 → コメントで代替/docs PRにまで重い再検証をしてクレジット浪費

## S3. delegate-subagent(分身への委任)〔①③〕

- **スキル名**: delegate-subagent
- **発動条件**: Issueを別モデルの分身に振るとき
- **入力**: Issue番号+担当モデル(docs/ORG.md v2 の担当表で決定)
- **手順**: 10行以内のプロンプトで起動: 「`cd <正本パス>` → `git checkout -B issue/... origin/main` → Issue #N を読んで実装。規約=AGENTS.md、運用=ORG.md。**進捗は意味のある単位ごとに commit+push**。最終報告は3〜4行」。並列は最大2体
- **判断基準**: Cursor→Sonnet→Opus→Fableのコスト階層順に「これで足りないか」を上から検討。調査と実装は分ける。同じファイルを触るIssueは並列させない(直列 or ブランチ分離を明示)
- **出力**: 分身の最終報告(数行)+push済みブランチ
- **失敗しやすい点**: **途中死で未コミット成果が全損**(即コミット原則を必ずプロンプトに入れる)/worktreeが `~`(ホーム)基準で作られ「not a git repository」→ プロンプト冒頭に正本パスへのcdを明示/ブランチ名が並行セッションと衝突(`issue/`プレフィクスで回避)

## S4. salvage-worktree(死んだ分身の成果回収)〔①③〕

- **スキル名**: salvage-worktree
- **発動条件**: 分身がセッション上限・プロセス終了で死んだ通知が来たとき
- **入力**: 死んだ分身の worktree パス(通知に含まれる)
- **手順**:
  1. `git -C <worktree> status --short && git log --oneline -3` で残存物を確認
  2. 成果物の品質を自分で検証(テスト実走・中身の読解)— 死んだ分身の自己申告は存在しない前提で
  3. 不足分(ノート・テスト・コミット)を仕上げ → worktree内から commit・push・PR
  4. `git worktree remove --force` + 不要ローカルブランチ削除
- **判断基準**: 「ほぼ完成(検証だけ残)」なら回収、「着手直後」なら worktree を捨てて再委任の方が安い。判断材料は diff の量と質
- **出力**: 通常のPR(回収した旨をコミットメッセージに書く必要はない)
- **失敗しやすい点**: 回収前に worktree を掃除してしまう/worktree のテストが main の `npm test` に混入して件数が水増し(vite.config の test.exclude で遮断済み)

## S5. resolve-pr-conflict(機能生存保証つきコンフリクト解消)〔①③〕

- **スキル名**: resolve-pr-conflict
- **発動条件**: PRが CONFLICTING になったとき
- **入力**: PR番号
- **手順**:
  1. PRブランチをcheckout → `git merge origin/main`
  2. 競合を解消。**「どちらか一方を採る」のではなく、両ブランチの意図を列挙してから統合**(例: HEAD側のmoonSign追加とmain側の立春引数追加を両方残す)
  3. `npm test` + **両方の機能をnodeワンライナーで生存確認** → merge commit → push
- **判断基準**: 競合箇所ごとに「この行はどのIssueの成果か」を特定できるまで git log/blame で遡る。特定できないまま機械的に解消しない
- **出力**: CLEAN になったPR+生存確認の実行結果
- **失敗しやすい点**: import行やctx分割代入の競合で片方の関数が静かに消える(テストがあれば検知できる — テスト先行整備が効く)/解消後にテストを回さない

## S6. browser-verify(ブラウザ実機検証)〔①④〕

- **スキル名**: browser-verify
- **発動条件**: UI に影響するPRの検証時のみ(計算・docsのみのPRでは発動しない)
- **入力**: 対象ブランチ、確認したい画面/機能
- **手順**:
  1. `npm run build` → preview を空きポートで起動
  2. フォーム入力は `form_input`/JS直接実行(1990-05-15 を標準テスト誕生日に)→ 診断実行
  3. JSで機械検査: `document.body.innerText.includes('undefined')` が false、対象要素の存在、375px時 `scrollWidth === clientWidth`
  4. スクリーンショットは **1PRにつき1枚まで**(画像トークン節約)→ サーバーkill
- **判断基準**: 文字列検査で済むものにスクショを使わない。オフライン検証はサーバーをkillして transferSize===0 を見る(本物のオフライン)
- **出力**: 機械検査のJSON結果+スクショ1枚
- **失敗しやすい点**: read_page が年セレクタ全option(数千トークン)を吐く → interactive filter か JS直接実行で回避/type アクションが日本語入力に失敗 → form_input を使う

## S7. fortune-audit(占術計算の流派監査レポート)〔②⑤〕

- **スキル名**: fortune-audit
- **発動条件**: 新しい占術体系の追加時、または既存体系の正確性に疑義が出たとき
- **入力**: 対象体系名、実装関数(calculations.js)
- **手順**: ①実装の式を抜粋 ②主要流派をWeb照合(出典URL必須) ③ズレる実例を具体的な生年月日で最低3件 ④「現状の式/主要流派/ズレる実例/推奨対応(おすすめ付き)」の表に集約 ⑤`docs/audit/` に保存
- **判断基準**: **どの流派を正とするかは決めない**(経営判断=人間)。Web照合できない主張は必ず[未確認]を付す。断定トーン禁止。商標(動物占い®等)はコンテンツ転載と計算方式の整理を区別
- **出力**: docs/audit/ のレポート+経営判断が必要な論点の選択肢表
- **失敗しやすい点**: 調査分身がWeb上限で死ぬ前提で「1件確定ごとに即ファイル追記+コミット」を怠る/おすすめを書かずに丸投げする(選択肢+メリデメ+おすすめが依頼主の要求水準)

## S8. calc-test-pin(計算テストの期待値3分類)〔②③⑤〕

- **スキル名**: calc-test-pin
- **発動条件**: calculations.js にテストを追加・変更するとき
- **入力**: 対象関数、期待値とその出どころ
- **手順**: 期待値に必ず出どころタグをコメントで付ける — [既知値](AGENTS.md等ドキュメント由来)/[外部照合](一般に知られる暦の事実)/[回帰ピン](現状実装の固定=正しさの保証ではない)。今日依存の関数は `vi.setSystemTime`、月相系はタイムゾーン依存なので幅を持たせる
- **判断基準**: 回帰ピンとの不一致はピン側の更新を検討してよいが、既知値・外部照合の不一致は実装バグとして報告(勝手に期待値を曲げない)。バグ挙動は「バグ報告テスト」として固定し、修正時に期待値へ書き換える
- **出力**: タグ付きテストケース+`npm test` 実出力
- **失敗しやすい点**: **ロケールスタブ(`setup-locale.js`)を calculations.js より先に import しないと ja 辞書が引けず全滅**(docs/learnings/vitest-locale-stub.md)/シグネチャ変更時に呼び出し元の直し忘れ(整合性テストで検知する — docs/learnings/i8-risshun-callsite-gap.md)

## S9. i18n-sync-check(ja/en同期の機械チェック)〔③④〕

- **スキル名**: i18n-sync-check
- **発動条件**: `src/i18n/locales/` 配下の文言を追加・変更したとき(毎回)
- **入力**: なし(リポジトリ全体)
- **手順**: nodeワンライナーで ja/en 両バンドルのキーを再帰走査し、片側にしかないキーを列挙。既知の意図的非対称(ローマ字欄=ja専用の6キー)は除外リストで許容
- **判断基準**: 新規変更由来の非対称は0件であること。トーン(断定しない・ネガティブ断定禁止)は機械チェック不能なので目視レビュー項目として分離
- **出力**: 「このPR由来の非対称 0件」の実行結果(PR本文に貼る)
- **失敗しやすい点**: 片方だけ直して「あとで同期」が残る(同一コミットで両方触るのが原則)/content.js(旧構成の名残)を正と誤認する — 正は i18n/locales 配下

## S10. gh-issue-pr-templates(Issue/PR/レビューの定型文書)〔⑤〕

- **スキル名**: gh-issue-pr-templates
- **発動条件**: Issue作成・PR作成・レビューコメント記録のとき(毎回)
- **入力**: 内容の要点のみ(形式はテンプレートが持つ)
- **手順**: Issue=6節構造(背景/最初に読む/やること/受け入れ基準/エスカレーション/依存)+ラベル `agent:*`(担当)`phase:*`(段階)。PR本文=対応Issue(Closes #N)/内容/検証(実行結果)/レビュー観点。レビュー=チェックリスト+「マージ可」判定+マージ後のISSUES.md更新依頼
- **判断基準**: 受け入れ基準は「実測可能」な文で書く(「テスト全pass」「横スクロール0」)。担当変更(エスカレーション)時はラベル付け替え+理由をコメントで残す
- **出力**: 統一フォーマットのIssue/PR/コメント
- **失敗しやすい点**: `Closes #N` を書き忘れてIssueが自動クローズされない/GH番号とISSUES.mdのI-番号の混同(PRでは必ずGH番号)

## S11. repo-housekeeping(作業ツリーの定期整理)〔①④〕

- **スキル名**: repo-housekeeping
- **発動条件**: `git status` に自分の作業と無関係な項目が現れたとき/フェーズの区切り
- **入力**: なし
- **手順**: ①各項目の由来を `git log --follow`・参照grepで特定 ②分類: 誤生成の複製=削除確定/コード参照のない大容量素材=gitignore(ファイルは残す)/一時ディレクトリ=gitignore ③マージ済みブランチとworktreeを削除 ④コミットは housekeeping 単独で(機能変更と混ぜない)
- **判断基準**: **削除とignoreを区別する**(復元できないものは消さない)。由来が特定できないファイルは触らず報告。5MB超のバイナリはリポジトリに入れない
- **出力**: クリーンな `git status`+整理内容のコミットメッセージ
- **失敗しやすい点**: 並行セッションの作業中ファイルを「ゴミ」と誤認して消す(reflogとブランチ全確認が先)/ignoreパターンが広すぎて必要ファイルまで隠す

## 補足: スキル化を見送ったもの

- **流派・方式の選定**(I-1型の意思決定): 毎回内容が異なる経営判断であり、手順化すると「AIが勝手に決める」事故の温床になる。選択肢提示までを S7 が担い、決定は常に人間
- **モデル切替のタイミング**: ORG.md v2 R5 のルール(節目のみ)で足りる。スキルにするほどの手順がない
