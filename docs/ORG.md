# ORG.md — cosmic_id 開発の組織設計(モデル別分担とレビューフロー)

作成: 2026-07-08(Fable 設計)。Issue の実体は `docs/ISSUES.md`、Cursor への委任は `docs/CURSOR-BRIEFS.md`。

## 役割分担(誰に何を振るか)

| 担当 | 向いている仕事 | このプロジェクトでの担当 |
|---|---|---|
| **人間(Koyo)** | 経営判断・最終責任 | 流派の採否、既存ユーザーへの結果変動の告知方針、法務(商標)、課金、PRの最終マージ |
| **Fable**(提供終了まで) | 一発で正しい判断が必要な仕事 | Issue設計(完了)、全ユーザーの結果が変わる計算修正のレビュー、品質ゲートの最終判定 |
| **Opus** | 正確性が要る調査・実装 | Web照合による検証、暦データ作成、計算式の修正、Fable 不在時のレビュー代行 |
| **Sonnet** | 手順が明確な実装 | バグ修正(テスト固定済みのもの)、文言・注記、CSS、PWA、コマンド実行 |
| **Cursor** | エディタ内の反復修正 | styles.css 中心のデザイン改善、375px 対応の実装部分(`.cursor/rules/` が規約を強制) |

原則: **調査と実装は分ける**(同一 Issue 内でも別ステップ)。**検証は作業した本人以外**(まっさらな別の分身 or 上位モデル)。

## 実装フロー(全 Issue 共通)

1. **着手**: 担当モデルが Issue の「最初に読む」を読み、`main` からブランチを切る(`issue/<番号>-<slug>`)
2. **実装**: 一番シンプルに。計算を触ったら `npm test`、文言は en/ja 同期、UI は 375px 確認
3. **PR 作成**: 本文に「実行結果(テスト出力そのまま)」「未確認事項」「受け入れ基準との対応」を書く
4. **レビュー**: レビュー担当が `/review <PR番号>` を実行し、下の品質ゲートで判定
5. **マージ**: 人間が最終確認してマージ(結果が変わる修正は告知文とセットで)

## 品質ゲート(レビュー担当のチェックリスト)

- [ ] `npm test` の実出力が PR に貼られていて全 pass(計算変更なら新旧の期待値差分も)
- [ ] 受け入れ基準を全て満たす。満たせない項目は「未確認」と明記されている
- [ ] AGENTS.md の禁則(escapeHtml / プレミアムロック / 関心の分離)を破っていない
- [ ] 計算式の変更に「○○流の式に従う」コメントがある
- [ ] 依頼範囲外の変更が混ざっていない(混ざっていたら分割を要求)

## エスカレーションルール(品質が足りないとき)

- レビューで**軽微な指摘**(文言・漏れ)→ 同じ担当が同 PR 内で修正
- **同じ Issue で2回差し戻し**、または**根本的な設計誤り** → 担当を1段上げて再実行:
  **Sonnet → Opus → Fable(提供終了後は Opus + 人間ペア)→ 人間**
- 上げるときは PR を閉じ、Issue に「何が足りなかったか」を1行残してから再アサイン(次の担当の入力になる)
- 逆に、上位モデルの Issue でも「調査で白黒ついて作業が定型化した」ら1段下げてよい

## レビュー担当の指名

- 計算式・全ユーザーの結果が変わる PR: **Fable**(終了後: Opus。その場合は人間が受け入れ基準の照合まで行う)
- それ以外(CSS・文言・PWA・注記): **Opus**(Sonnet の自己レビュー + 品質ゲートで可)
- Cursor の成果物: 変更が styles.css / index.html に閉じていることを **Sonnet** が確認し、375px スクリーンショットで判定

## GitHub Issues 運用(2026-07-10〜)

16件を https://github.com/tannyann/cosmic-id/issues に作成済み(#1〜#16、`docs/ISSUES.md` に対応表)。
ラベル: `agent:{human,fable,opus,sonnet,cursor}`(担当)/ `phase:{0-decision,1-research,2-fix,3-ui,4-ops}`(段階)。

- ブランチ名は `issue/I-<番号>-<slug>`(例: `issue/I-5-tarot-fix`)
- PR本文に **`Closes #5`** と書く(GitHubのIssue番号。ISSUES.mdのI-番号ではない)→ マージで自動クローズ
- エスカレーションで担当を変えたら、Issue自体のラベルを付け替える(`agent:sonnet`→`agent:opus`)。理由をIssueにコメントで残す
- `docs/ISSUES.md` の状態列は都度手動同期(GitHub側のOpen/Closedが正)

## 運用の約束

- Issue の状態は GitHub Issues(#1〜#16)を正とする。`docs/ISSUES.md` は設計書として都度反映
- 学びは `docs/learnings/` に1件1ファイル。誤りだったものは消す
- サブエージェント並列時は書き込み先を分け、成果物は途中でもファイルに書かせる(途中死対策)
